# A15 CPU 计分核对与横屏黑屏修复（2026-10-14）

设备：iPhone 13 Pro / Apple A15，iOS 27.0.1。只测试当前 iPhone；未重测其他设备。

## 结论

此前的大核 146.994、小核 26.740 不能作为同一种满负载条件下的每核成绩相加：
`2 × 146.994 + 4 × 26.740 = 400.948 MWork/s`，与此前全核 661.557 不一致。
大核使用交互优先级，小核为了获得可验证的 E 类型归属使用后台优先级；全核
启动六个系统调度线程，未给它们设置后台优先级。类型验证不等于峰值性能验证。
此前把小核 26 分直接解释为正常满负载小核能力，会造成错误理解，现已明确标注。

增加每轮各线程实际工作量后，两轮原工作负载复测均通过，全核各贡献之和等于
所选中位轮的总分，没有把三轮加在一起，也没有重复计分。计分公式没有更改。

| 复核轮次 | 大核单线程 | 小核单线程（后台） | 全核六线程 |
| --- | ---: | ---: | ---: |
| 算力核对 | 147.029 | 27.009 | 642.251 |
| GPU → CPU 界面切换验证 | 146.674 | 26.706 | 663.715 |

单位均为 MWork/s。均沿用 15 秒、0.2 秒预热、三轮取中位数；热状态全部 0→0。
前者选中第 3 轮，六线程贡献为
`108.168876 + 106.896667 + 106.650089 + 106.769692 + 107.699477 + 106.066004 = 642.250805`。
后者为
`110.951801 + 110.518447 + 110.079358 + 110.724884 + 110.901011 + 110.539746 = 663.715247`。
JSON 总分保留三位小数。线程会在核心间迁移，这六个贡献不能分别标为六个物理核心。

首轮小核每轮五秒内实际 CPU 时间约 4.925、4.793、4.954 秒，至少 99% 属于 E 类型。
低分主要不能用“没有得到 CPU 运行时间”解释。后台政策与全核不同是已确认的测量条件；
其对吞吐的影响符合 [Apple QoS 说明](https://developer.apple.com/documentation/dispatch/dispatchqos/qosclass-swift.enum)。
本次没有独立测量 iOS 主频，不能声称测到了确定的小核 GHz，或由总分反推小核峰值。
全核公共进程计数包含其他应用线程，只作诊断，不用它给每个全核线程认证 P/E 归属。

## CPU 缓存为什么横屏黑屏

一键全套及自动化子集共用了 GPU 全屏容器。原容器始终要求横屏、以黑色为背景，
CPU 阶段没有渲染画面，只在顶部显示一条状态。分类内存扫描又需暂存日志来减少
核心归属测量的干扰，因此持续几分钟看起来像黑屏。

已修复：只有实际绘制的 GPU 项目要求横屏；手机的 CPU、无画面计算和缓存／内存
项目恢复竖屏，显示测试名称、进度说明、状态和停止按钮。Metal 画面仍保持附着，
但在无画面项目中隐藏。CPU 阶段点击页面不会误触取消。启动前不再读取占位的
GPU 项目并短暂旋转；iPad 无画面阶段跟随设备方向。

完整 CPU 缓存、内存、页面首次触碰和存储复测通过，全核内存读取 34.834 GB/s。
大核／小核各 93 个读写复制曲线点（合计 186）均通过至少 99% 归属验证，
全核曲线也保存。页面测试是首次页面映射／分配，不等于实际换出、换入测试。
最终安装版本再次通过 GPU → CPU 切换：GPU 截图 2532×1170，CPU 截图 1170×2532。
