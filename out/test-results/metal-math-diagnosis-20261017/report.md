# M4 Pro GPU Burn 诊断 · 2026-10-17

**已完成待办 M5：主要差距定位到完整着色器的末尾 discard／可见性执行路径，
而不是片元阶段天然只有计算阶段的三分之二。**控制实验和 Xcode 硬件计数器支持

## 1. 常量 FMA：小幅差异，未证明峰值

原样探针 fast：缓冲参数版 **6.783 TFLOPS**，字面常量版 **7.291 TFLOPS**，
后者快 7.48%。precise 为 7.065 / 7.109 TFLOPS。
初次运行可能受启动频率和运行顺序影响，因此另用同一 4096 次迭代、同样七次
中位数，预热后按“缓冲→常量→常量→缓冲”确认：

| 轮次 | 缓冲参数版 TFLOPS | 字面常量版 TFLOPS |
| --- | ---: | ---: |
| 正向 | 6.784 | 6.984 |
| 反向 | 6.849 | 7.076 |
| 两轮平均 | 6.817 | 7.030 |

配对平均差 **3.13%**。没有复现 RTX 5090 上常量版约 33% 的提升，不能用这个
因素解释 M4 Pro 的主要 Burn 差距。两种都是特定 FMA 内核的吞吐，不能称硬件峰值；
没有测量 GPU 实际频率，也不把首轮低值确定归因为降频。

## 2. 简化片元循环几乎和计算循环一样快

初次自动校准：计算循环 **14.674**、片元循环 **13.384 Gpix-step/s**，比例 91.2%；
但两者分别用了 793 / 737 步，不能据此精确归因。随后在相同步数、相同相位测量：

| 相位 | 步数 | 简化计算循环 | 简化片元循环 | 原样完整着色器两遍 |
| --- | ---: | ---: | ---: | ---: |
| 0.999 | 64 | 14.561 | 14.279 | 9.390 |
| 0.999 | 256 | 14.616 | 14.275 | 9.409 |
| 3.000 | 64 | 14.569 | 14.277 | 9.405 |
| 3.000 | 256 | 14.573 | 14.340 | 9.429 |

单位均为按提交的像素步数计算的 Gpix-step/s。256 步时简化片元为计算的
**97.7–98.4%**，完整着色器为 **64.4–64.7%**。完整着色器直接读取仓库中的
`shaders/gpu_burn.metal`，没有改源码；每帧两个 draw，参数 ABI 和版本 3 相同。
完整图像读回有颜色变化，原始哈希见日志。

16 步也有完整数据；第一项计算时间 1.529 ms，七次范围 1.026–3.932 ms，
启动波动明显，未丢弃或重跑挑分，不用这一项作精确比值。初次与后续控制轮的
完整两遍 256 步范围约 8.81–9.43；各轮均完整保留，不替换已有正式成绩。

## 3. 抓帧：额外片元执行，比寄存器占用更有解释力

通过 `MTLCaptureManager` 保存简化计算、简化片元和完整两遍三个负载，
在 Xcode 中 Replay 并 Profile，导出界面文字、CSV 和截图。
工具链的指令级源码分析组件未安装，但硬件计数器和寄存器统计正常可读；
未安装额外组件。[Apple 抓帧流程](https://developer.apple.com/documentation/xcode/capturing-a-metal-workload-programmatically?language=objc)。

| 着色器 | 分配寄存器数 | 溢出字节数 | FS 调用次数 | FS 占用率 |
| --- | ---: | ---: | ---: | ---: |
| 简化计算循环 | 72 | 0 | 不适用 | 不适用 |
| 简化片元循环，一遍 | 68 | 0 | 921,600 | 85.79% |
| 原样完整着色器，两遍 | 134 | 0 | 2,785,280 | 90.18% |

两遍提交的像素数为 **1,843,200**，完整着色器 FS 调用多 **51.1%**。
寄存器确实较多，但没有溢出，而且该捕获中的 FS 占用率没有更低，不能把
“寄存器更多”直接写成“占用率更低导致慢三分之一”。

正式着色器末尾按 `haloMask` 调用 `discard_fragment()`，该掩码依赖完整计分循环。
Apple 的 TBDR 可见性处理会受 discard 影响；硬件可能为确定可见性执行着色器工作。
这一机制方向有 [Apple GPU 架构说明](https://developer.apple.com/videos/play/wwdc2020/10602/)
及[计数器使用说明](https://developer.apple.com/videos/play/wwdc2020/10603/)支持。
本次对内部执行方式的判断仍是计数器和控制实验推断，没有取得逐指令汇编轨迹。

## 4. 仅在诊断副本去掉 discard 的控制

诊断工具运行时从同一正式源码复制一个字符串，只把唯一的 `discard_fragment();`
换为空语句。正式文件未改；循环、后续着色代码及参数保持原样。
相同的单 draw 排除“另一遍被完全遮住”的影响：

| 相位，256 步 | 原样单遍 ms | 无 discard 单遍 ms | 时间比例 |
| --- | ---: | ---: | ---: |
| 0.999 | 35.709 | 18.391 | 1.942 |
| 3.000 | 35.597 | 18.468 | 1.927 |

单遍几乎减半，说明末尾 discard 的执行路径确有大成本。后续独立捕获中，原样
两遍 FS 调用 **2,756,032**，仍比两遍像素数多约 **49.5%**，ALU 指令约
**2478 亿**；无 discard 两遍只有 **889,952** 次 FS 调用、约 **864 亿**条 ALU 指令。
后者接近一屏，说明不透明第二遍遮住第一遍后，GPU 能剔除第一遍工作。
这些调用计数会随 profiler 的统计方式有少量变化；两次原样捕获的主要结论一致。

**不能把无 discard 两遍的 25–26 数字当成改进后的正式分数。**它按“提交两遍”
计算分子，实际只执行约一屏，图像语义也已改变；直接删掉 discard 会破坏原本
“两遍均有可观察工作”的要求。它仅用于定位，未写进 `results.json`。
无 discard 副本仍分配 126 个寄存器，未降至简化片元的 68 个；寄存器差异不足以
单独解释观察到的执行次数变化。

因此，此前仅凭 16/64/256 线性拟合就断言“循环后着色及每帧两遍已排除”的说法
过强：小截距不能排除它们改变整段着色器的编译和可见性执行。当前结果支持
完整着色器的 discard／可见性路径是主要因素，未证明能解释所有设备/API 的分差。
