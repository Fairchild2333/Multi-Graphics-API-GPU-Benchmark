# M4 Pro 单核：独立基准与内核诊断 · 2026-10-17

**这台Mac实际Geekbench 6.7.1单核3675、多核22129。当前项目的MWork/s主要测
串行混合内核，不代表综合单核能力。**独立单核仍比约3900的公开样本低约6%，
本轮没有确认这部分差距的原因，不能据此宣称机器达到峰值或完全排除系统因素。

本轮完成一次获用户明确授权的Geekbench CPU测试，以及四组隔离诊断。
没有修改App测法、分数、编译设置或验收门槛，没有反复跑Geekbench挑最高值。

## 本机独立结果

[本机公开成绩19350647](https://browser.geekbench.com/v6/cpu/19350647)：
Geekbench 6.7.1，macOS AArch64，Mac16,8，14核M4 Pro，48 GiB，macOS 27.0.1。
单核3675、多核22129；16个单核和16个多核子项保存于`geekbench-result.json`。

原生CLI实际运行约4分钟，退出0，上传成功；测试前后热状态均为nominal、
低电量模式关闭，使用AC供电。没有更改电源设置。期间一次进程快照中只有
Geekbench达到20%以上CPU占用；这不是对所有系统干扰或全过程温度的连续监测。
其他性能测试在Geekbench结束后才开始。

公开参考仅作样本比较，不是官方额定分数或同条件统计分布：

## 编译与分支诊断

安装包对应的实际Release参数是`-O3 -DNDEBUG`，并非Debug。
从生产`src/cpu_benchmark.cpp`原样提取混合内核，构建独立诊断程序，使用大核QoS，
通过线程计数验证大核驻留和执行占用。固定矩阵为两种编译目标×两种分支模式，
每组3轮，每轮2秒、预热0.2秒，取中位数。完整代码、命令、12轮日志及汇编入库。

| 编译目标 | 分支模式 | 诊断MWork/s | 选中轮周期/单元 |
| --- | --- | ---: | ---: |
| 默认arm64 | 原伪随机条件 | 225.621 | 19.014 |
| apple-m4 | 原伪随机条件 | 224.871 | 19.014 |
| 默认arm64 | 固定规律交替 | 423.492 | 10.355 |
| apple-m4 | 固定规律交替 | 419.501 | 10.391 |

默认与M4目标的原负载差-0.33%，固定批次数校验和一致，没有发现遗漏M4编译目标
造成巨大损失的证据。两种目标、两种模式的四个函数均保留真实bit0分支和
FP32/FP64 FMA，函数内没有csel/fcsel；规律分支并未被编译器直接删掉。

改变分支规律后，默认目标吞吐增加87.70%，周期/单元由19.014降至10.355。
这直接支持当前内核对分支/数据依赖模式敏感；没有测硬件branch-miss计数，不能
断言实际错误预测率正好50%，也不能把全部周期差当成精确的分支恢复代价。

**225/423都是隔离诊断值，不替换App的216.737。**诊断采用独立调用函数和较短轮次，
编译上下文、计时外层与正式App不同；规律分支还改变了负载，不能冒充正式复测。

## 为什么不能当综合单核

当前内核每一步依赖前一步，使用标量整数、FP32/FP64及伪随机分支，没有独立的
SIMD、矩阵、压缩、编译、图像处理子项。Geekbench覆盖多种实际负载，并允许
使用SIMD/矩阵指令；厂商从6.3起为机器学习子项加入SME内核，M4可受益于此。
这解释了两套指标覆盖不同，不证明SME或分支单独解释全部差异。
见[Geekbench方法](https://www.geekbench.com/doc/geekbench6-benchmark-internals.pdf)、
[SME版本说明](https://www.geekbench.com/blog/2024/04/geekbench-63/)、
[Arm关于M4的SME2支持](https://developer.arm.com/mobile-graphics-and-gaming/ai-mobile)。

应将现有成绩解释为“串行混合内核吞吐”。若以后提供综合CPU成绩，需要独立定义
跨平台多子项、校验和版本合同；不能乘系数贴合Geekbench、用规律分支替换旧
随机分支后沿用原版本，或把不同负载的成绩混排。本轮没有增加这些新测试。
