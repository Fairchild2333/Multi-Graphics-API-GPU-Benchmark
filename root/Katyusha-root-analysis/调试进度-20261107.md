## 本会话结论（按证据强度）

### 1. W1 失败完整复现（与 10 月五份日志同点）

### 2. 假设 A 实验（E1/E2）——窗口预算与 enforce 探针

**E1a 发现（代码级，确凿）**：multicast 路主线程
`multicast_waiter_route.cpp` 在 `consumer_calls == 0` 的自旋后**立即** `consumer_go.store(0)`
——consumer 整个竞态窗口只开一炮，profile 的 `select_consumer_max_calls` 在该路完全失效
（本次日志 `calls=1`，profile 改 64 后依然 `calls=1`，铁证）。

**E1b（第一次内核崩溃）**：修掉关窗逻辑（等 consumer 跑满预算再关窗）+
profile 64 发 → 进程在 "waiting route_done" 处随设备从 USB 消失——**项目史上第一次
内核 panic**。单发从不崩（6+ 次）、64 连发必崩（2/2），说明 consume 确实把 PI 链走深了。

**E2（enforce 探针）**：consumer 每炮后读 `/sys/fs/selinux/enforce`，翻转即停窗 →
仍崩。崩溃发生在 sched_setattr **syscall 内部**（erase 落地后链继续行走踩到
fake_task 页垃圾字段），用户态轮询来不及。

### 3. 假设 B 获代码级实锤

`encode_multicast_waiter`（payload_builder.cpp:49）**只写 task(+48)/lock(+56) 两个字段**，
stale waiter 的 tree_entry(+0x00/08/10) 与 pi_tree_entry(+0x18/20/28) 六个树字段被
stamp 的 memset 清零后从未填入写参数。对比 skb 路的 `encode_compact_waiter`
（:35-47，会填 0x18/0x20/0x28 三字），两条路的实现差距就是假设 B 的缺口。

页面侧 fake W0 的 pi_tree_entry 由 `encode_compact_waiter` 正确填了
`{parent=target-8, right, left}`（W1 = 全 0 值 → 擦除走 __rb_change_child else 分支
写 `*(target) = NULL`，机制自洽）。

### 4. 取证受限（结构性）

5 Pro 无 root（GhostLock 从未完整成功）、无 TWRP（stock recovery）、EDL 收费墙——
panic 的 ramoops **无法读取**。全程盲调。3 Pro 那套 EDL 取证流水线在此机不可用
（SM8450 = 骁龙 8 Gen 1 起 firehose 强制工号授权，2026-11-07 网查确认仍无公开绕过）。

### 5. 附带确认

- KTUS-A0 解锁：免费无路（EDL 授权墙 + 官方渠道死 + 社区无引导链落地）；
  付费授权服务存在（B 站/淘宝，几十到几百元）但锁机强开有变砖风险。
- SM8450 = 骁龙 8 Gen 1；EDL 授权墙从黑鲨 4 代/该代 SoC 开始，3 Pro（SM8250/865）是最后一代免费 EDL。
- 手机每次崩溃后均完整恢复（重启约 15-40 秒，stock boot 无持久损伤），共崩 2 次。

## 2026-11-08 会话（E3 实现→E4/E5 实验）

### E3 实现（上个会话完成的代码，本次确认）
`encode_multicast_waiter_trees`（payload_builder.cpp:68）+ multicast 路调用点（multicast_waiter_route.cpp:54）：

（"E3: tree fields planted"），随后 panic（设备掉线重启）。

### E4（闭环撤除实验）
撤除上个会话的闭环植入（util.cpp:457-461 恢复空 pi_waiters = 10 月设计）→
**不再 panic** ✓（闭环被确认为 7-8 炮崩溃的源头）——但 W1 仍失败（calls=4，无翻转）。

### E5（零写编码实验）
`encode_compact_waiter` 的 W1（Zero 模式）pi_tree 编码改为零写形式
`{pc=(target-8)|RED, 0, 0}`（原编码 relink 会把页指针写进 *(target)）→
仍无翻转（4 炮窗口）。无 panic（闭环撤除后保持稳定）。

### 源码级机制确认（rtmutex.c v5.10.101 实源核对）
- 写入机制：rt_mutex_dequeue_pi(task, waiter) → rb_erase_cached(&waiter->pi_tree_entry,
  &task->pi_waiters)——擦除用的是**被擦 waiter 自己的 pi_tree_entry 字段**（我们的参数）
  → parent=target-8、RED 叶、无子 → __rb_change_child 的 else 分支写 NULL 进
  parent->rb_right = target → *(target)=0 ✓ 编码正确。
- 触发机制：链行走 [11] 的 dequeue_pi 仅在 waiter 位置变化（成为新 top / 失去 top）
  时触发——[7] requeue 的门槛 `rt_mutex_waiter_less(task_prio, fake_w0_prio=140)`：
  waiter_task 的 prio（120-139）< 140 ✓ 门槛通过。
- **未解之谜**：机制全通但 enforce 不翻转。怀疑点（无取证无法验证）：
  (a) stamp 的 512B 覆盖窗（waiter_off=320、buffer=528）与实际 stale waiter 深度的对位偏差；
  (b) fake_lock->waiters 根指向 fake_w0 的 tree_entry（非 pi_node），[11] 擦的是 pi_tree_entry
  ——树根与被擦节点不同槽位，rb_erase_cached 的路径可能读不到我们的参数；
  (c) stale waiter 在真实 futex 队列的 linkage 与我们植入字段的相互作用。

### 结论与建议
盲调每轮 30-60 分钟 + 一次 panic 风险，机制推演与实测反复矛盾——**缺取证是根本瓶颈**
（BL 锁定 → TWRP 无法引导 → ramoops 不可读 → EDL 收费墙）。建议：
1. 付费解锁（几十到几百元）后一切 opens（root/TWRP/取证/GApps 一次全解决）
2. 或将 5 Pro 研究挂起，跑分机用 sideload 方案
本会话产物：ghostlock-run-20261108-4/5 日志 + E3/E4/E5 全部代码改动（工作树未提交）。

## 2026-11-08 会话 2（GhostLock app v590：从"无法执行"到真实 panic）

背景：14:40 装上 app v590/1.2（UI 含参数配置/解析器/调试日志导出）。用户 16:45 前跑了
一轮解析→自动加载，执行按钮灰 + 横幅"配置需要修正"——这就是"ghostlock 无法执行"的真相。
本会话用模拟点击（adb input）逐屏诊断并全部修复。

### 执行被禁的根因链（按发现顺序，四层全修）
1. **内置解析器产物是骨架**：15:22 "解析本地镜像"生成的 conf 只含 offset 类字段，
   DRAM 物理基址、cred 整块（copy_size/caps/ref0-3）、结构布局全空 → 校验红。
2. **release 严格比对 uname**：手工 conf 写 `5.10.101-android12-9-gece0cc04d1a5-ab15212794`，
   uname -r 是无后缀的 `5.10.101-android12-9-gece0cc04d1a5` → 导入被拒
   （"已导入，但 release 与本机内核不匹配，不会生效"）。10 月档案记的是完整构建串，踩坑。
3. **ref3 写 null 非规范**：make_profile 规范是 `ref3_offset=0/ref3_image=0`；
   ref_count=3 时校验器跳过 ref3，红行只是 null 的呈现样式。
4. **真正的拦路虎：路由分支缺失**——app 路由=multicast_waiter，10 月 conf 只有
   route.select_stack 分支，multicast 必填字段（buffer_size/task_offset/lock_offset 等）全缺。
5. **最终解**：按 tools/make_profile.cpp 当前值（今天 CLI 所跑同一套）生成完整 conf：
   route.multicast_waiter {waiter_off=320, buffer_size=528, task_offset=48,
   lock_offset=56, compact_waiter=1} + cred 修正（caps_offset=48/caps_count=3/
   caps_value=0x1ffffffffff/usage_value=256，10 月 conf 是 40/5/-1/1，以 make_profile 为准）
   + ref3=0/0 + 无后缀 release → 校验全过，绿色"受支持/配置已就绪"，执行解禁。
   - task_struct 的 pid/tgid/atomic_flags/tasks 保留 10 月非零值
     （validateMerged 对 task_struct/offset 的零值也报错）。
   - slide_loggers_0_1 采用 make_profile 的 43651656（10 月 conf 为 43651640，差 16B，待核）。
   - 成品归档：`katyusha-full.conf`（本目录）；app 内注册为 katyusha-full.conf（16:43）。

### 首次 app 运行 = panic（新签名，重要）
- 16:45:4x 模拟点击"执行"；后台 logcat 捕获 16:46:11 断流；设备 ~16:46:38 重启
  （uptime 19s，transport 27→28）——**tap 后 25-30 秒内核 panic**。
- 对比：CLI E4/E5（13:15-13:59）= 无 panic、W1 不翻转；app = panic。
  app conf 不带 execution 段，用 app 默认 consumer 窗口参数 → corruption 走得更深
  （E2 时代签名：erase 落地后链继续行走踩 fake_task 页垃圾 → panic）。
- 重启后 app 弹"上次攻击未完成（设备可能已内核 panic 并重启）"，配置状态跨重启完好
  （绿色受支持），说明 app 的中断检测与持久化都工作正常。
- 取证全灭：debug-log 目录未及写出（export 在运行收尾）；`/sys/fs/pstore`、`dmesg`、
  `run-as` 三路全权限拒绝——BL 锁定取证缺口第三次确认。logcat 尾部仅系统噪音。

### 结论与下一步
1. **"无法执行"问题已终结**：校验门是配置完整性问题，不是漏洞问题。
2. app 与 CLI 的 panic/无 panic 差异是新的实验杠杆：把 app 的 execution 旋钮
   （select_consumer_max_calls/burst 等）补进 conf 或在编辑界面调整，对齐 CLI E4/E5
   参数（4 发窗口、无闭环）→ 预期复现"无 panic 不翻转"，即可在 app 内做参数扫描。
3. v590 解析器只产 offset 骨架、不含 cred/结构布局——对新设备仍会卡校验门，记录为 app 已知局限。
4. W1 机制层障碍不变（指针环/擦除触发条件），取证缺口仍需解锁才能破。

## 2026-11-10 会话 4（E6a/E6b 实测：prio 门槛证伪，select 臂关闭）

### ⚠ 运维新坑：adb push 会被 panic 回滚（重要！
push 后几秒内若发生内核 panic，文件数据块还在页缓存、未过 journal 提交点 →
重启后 ext4 回放把文件滚回旧内容甚至消失。本会话实锤：12:07 推的 ghostlock/
make_profile/katyusha.bin 在 12:08 select panic 后全部回滚（ghostlock 变回 11-08 版、
katyusha-select.bin 直接消失）——第一轮"E6a 无打印"其实是旧引擎在跑。
**纪律：push 后必须 md5 校验 + `sync`，再跑可能 panic 的二进制。**

### 实测结果（4 轮，日志 ghostlock-run-20261110-1~4）
1. **E6a multicast（md5 校验后真跑）**：`E6a: stale waiter prio=140 planted at stamp+0x180`
   植入 ✓、无 panic、calls=4/4、**W1 仍失败** → **prio 门槛假说对 multicast 证伪**
   （prio+树字段+stamp 全就位仍不写）。
2. **select 配方（Poco F5 照搬，katyusha-select.bin）**：新旧二进制（split/flat word10）
   各一轮，**都在 pre-select attempt=1 处 panic** → select+compact 臂在 katyusha 关闭。
   注意 PR #721 的 select_stack_route 改动不止 word10 一处，本树只摘了一个 hunk，
   不完整移植可能是崩因；完整移植留作后续可选。
3. 排除法收敛：页侧"园艺"（链树/blocked_on/prio）推不出 stale waiter 的擦除——
   擦除必须来自 futex 路径本身（EDEADLK abort 的 dequeue 或 unlock_pi）。
   **下一步 E6d：consumer 在竞态窗口内改调 futex(FUTEX_UNLOCK_PI)（或 FUTEX_WAKE）**
   强制内核走 rt_mutex 清理路径 dequeue stale waiter（其 stamp=写原语）——
   即 11-08 另一位 AI 提的"促成出队"方案，现为首选项。

## 2026-11-10 会话 5（E6d/E6e/E7 + waiter word 数学：三个月死结的层定位）

### 实验记录（日志 5~9）
1. **E6d**（consumer 每炮必发 futex 走链，解除"仅 sched 失败才走"的门）：
   走链执行（LOCK_PI 超时 errno=110 证明真实入队+超时清理两次走链）、无写、偶发 panic。
2. **E6e**（槽位错配树链接：fake_task->pi_waiters.rb_node→页 W0 tree_entry(+0x00)、
   leftmost→pi_tree(+0x18)）：4 炮 panic；**单炮（calls=1/burst=1）不崩但也不写**。
3. **E7 可见探针**（`GHOSTLOCK_W1_TARGET` 环境变量把 W1 目标改指 sysctl_bootid 数据，

   → 写入原语从未执行过**——不是写偏，是擦除根本没发生。

### waiter word 数学（用 oneplus 变体方法论 + 本机反汇编，全部实测帧）
- futex 侧：sys_futex(0x90) → do_futex(0x20) **直调** fwrpi（同 oplus README "5.10 OPLUS" 模式）；
  rt_waiter 在 fwrpi 帧 sp+0x90（rt_mutex_wait_proxy_lock/cleanup 双调用实证）→ 绝对位 **B-0x1C0**
- pselect 侧：sys_pselect6(0xA0) → core_sys_select(0x1C0)，stack_fds=sp+0x50 → **B-0x210**
- **katyusha waiter word = +10 > 上限 7 → pselect 路线结构性不可行**：
  waiter 的 tree/pi_tree(+0x00~0x28)落在 ex 集可写区（word 10-14），但
  task/lock/prio(+0x30/0x38/0x40)落在内核清零的 res_* 区 → 走链 NULL 解引用
  —— 10 月 select 干净失败 + 本会话 select compact 双双 panic 全部解释。
- **sigreturn 窗口验证**：sys_rt_sigreturn(0x50) → restore_sigframe(0x60) →
  restore_fpsimd_context(0x30+0x220，缓冲在 sp、`mov x0,sp`+copy 0x200 实证) → 缓冲 **B-0x300**；
  waiter_off = (B-0x1C0)-(B-0x300) = **0x140 = 320 恰好正确**。悬案 (a)（stamp 对位）关闭。

### 结论与战略
- 层定位完成：stamp 层（对位 320 ✓、编码 E3/E6a ✓、prio ✓）全对；**死在消费层**——
  stamp 落在已死的 fwrpi 帧上后，没有任何内核路径再对它执行 rb_erase。
  oneplus 变体能写是因为 stamp 与活 waiter 同帧（pselect 拷贝窗口天然耦合），
  而 katyusha 的 pselect 窗口够不着 task/lock/prio。
- 选项 A：继续攻 multicast 消费层（活帧投递重设计：信号中断 + sigreturn 在 fwrpi 返回前
  完成？不可行——sigreturn 缓冲在信号帧上，比 fwrpi 更深）。
- 选项 B（**推荐**）：付费 BL 解锁（几十到几百元）——取证/TWRP/root/GApps 一次全开，
  跑分机队拿到 5 Pro 的 Vulkan 数据才是项目本目标；GhostLock 研究转为学习性质。
- 遗留资产：E7 探针机制（任何写入原语改动 30 秒可验）、waiter word 计算脚本、
  本机反汇编帧库（可复算任何窗口）。

## 2026-11-10 会话 6（E9/E10：终审判决——公开漏洞路线在 katyusha 上全部结构性不可行）

### E9 毒锁实验（判决性）
- util.cpp 把 fake_lock->wait_lock 植 1（"已锁"）。若任何链行走到达 [5]
  trylock(fake_lock->wait_lock)，consumer 会永久自旋、join 挂死。
- **实测：运行完全正常**（threads joined ✓、sched_setattr 秒回、Write 1 failed 照旧）。
- 结合 sched_setattr 成功 ⇒ `rt_mutex_adjust_pi` 的唯一早退分支命中：
  **`waiter_task->pi_blocked_on == NULL`——EDEADLK 中止被 5.10.101 干净清理，
  UAF 悬挂态从未成型**。multicast 路由的消费模型（悬挂指针引走链）对本机死胎。
  E1~E8 全部建立在这个不成立的前提上。（毒已撤，判据已记录）

### E10 tcp_zerocopy 路由（日志 11）
- 自带编舞（TCP_ZEROCOPY_RECEIVE 停靠帧 + fallocate puncher 竞态），不依赖悬挂态。
- 实测：**每炮 EINVAL（errno=22），内核把 optlen 改回 24**。破案：路由传
  optlen=0x40（载荷 waiter_task@zc+0x28 / fake_lock@zc+0x30 在结构体之外——为 6.x
  的宽松校验设计），**5.10 严格 `optlen == sizeof(zc) == 24` 直接拒绝**——第三条路由
  在 5.10 上结构性不兼容，且窗口即便兼容也只盖到 waiter 的 tree_entry（0x00..0x18）。
- 全程无 panic，boot_id 探针不变。

### 终审汇总：四条公开路线 × katyusha 全部结构性封死
| 路线 | 死因 | 判据 |
|---|---|---|
| select_stack（含 oneplus 变体） | waiter word=10 > 上限 7；task/lock/prio 落在内核清零 res_* 区 | 本机反汇编帧计算 |
| multicast_waiter | stamp 几何完美（waiter_off=320 ✓）但消费前提（悬挂 pi_blocked_on）被本内核清理 | E9 毒锁 |
| tcp_zerocopy | 5.10 严格 optlen==24 < 载荷需求（0x40） | E10 EINVAL + 源码 |
| DirtyFrag | shell 域被 sepolicy 禁止开 XFRM netlink | 11-08 实测 |

活 waiter 盖章在物理上不可达（自线程阻塞时无法发 syscall，信号路径窗口更深），
死 waiter 盖章无消费者——**katyusha 上不存在"投递窗口 × 消费路径"的可行组合**。

### 最终建议（不再摇摆）
1. **付费 BL 解锁**（几十到几百元）是 5 Pro root 的唯一现实路径；解锁后 root/TWRP/
   取证/GApps 全开，跑分机队收回 5 Pro。GhostLock 部分以"完整解剖报告"结案——
   本文档系列即为交付物。
2. 若坚持零成本：5 Pro 转纯跑分用途（sideload 装跑分 app），root 研究停止。
